# Автодоставка Paranoia в Codex

Режим `mcp codex-channel` доставляет сообщения одной темы в заданный thread Codex.
Работает отдельным процессом EasyCli, в том числе когда агент завершил ход.

## Посылки

- Codex 0.157.0 принимает [app-server RPC](https://learn.chatgpt.com/docs/app-server)
  через WebSocket на Unix-сокете уже работающего daemon.
- В этой версии `mcpServer/event/stream/start` для локального stdio MCP возвращает
  `MCP event subscriptions are only supported for hosted apps`. Проверено запросом.
- `thread/queue/add` сохраняет входящее и автоматически запускает свободную сессию.
  Повторный `clientUserMessageId` не подавляет дубли. При переносе из очереди в
  историю ID временно может отсутствовать в обоих ответах RPC. Это проверено
  отдельным локальным app-server с имитатором Responses API.
- Привязка по cwd недостаточна: несколько сессий могут работать в одном каталоге.

## Решения

- Сессия и тема задаются явно. Приемник не вызывает `thread/start` и не меняет
  `set_channel_topic`. После рестарта daemon возобновляет тот же ID через `thread/resume`.
- Общий лок пулера Paranoia сохраняется. Курсор доставки выделен по аккаунту,
  собеседнику, теме и thread. Отдельный лок темы запрещает второй приемник Codex
  на ту же тему. Имя собеседника сначала разрешается в server_id.
- Реакция получения отправляется перед `queue/add`, иначе быстрый ответ агента
  мог бы закончиться раньше реакции. Она означает прием каналом, не начало работы
  модели. Факт реакции сохраняется; восстановление не заменяет ею поздний статус.
- Перед RPC сохраняется `pending.submitted`. Курсор двигается после успешного
  ответа или обнаружения ID в очереди/истории. При неизвестном исходе автоматической
  повторной отправки нет. Только `-32601` и `-32602` означают отказ до принятия;
  internal error и обрыв транспорта требуют сверки.
- Запись состояния использует fsync файла, rename и fsync каталога. Нечитаемый
  курсор не заменяется пустым. Первой привязке нужен ID уже обработанного сообщения;
  следующий запуск использует сохраненный курсор и игнорирует начальную отметку.

## Компромисы и особенности

Неопределенный исход RPC приостанавливает следующие сообщения этой темы. Например,
процесс может завершиться между сохранением `submitted` и отправкой; либо сокет
может оборваться после проверки живости, но до приема запроса Codex. Приемник
продолжает искать подтверждение, однако отсутствие ID само по себе не разрешает
повтор. Сообщения остаются в сторе, курсор не двигается. Это защита от дублей с
явной остановкой при неопределенности, а не гарантия exactly-once.

Обычное отключение Codex до попытки отправки восстанавливается автоматически.
При удалении уже отправленного сообщения из Paranoia подтверждение ищется без
его текста. Отсутствие еще не отправленного сообщения считается удалением только
после проверки его seq по карте сервера. Этот запрос не двигает курсор приема и
не требует захвата роли пулера. Если сообщение на сервере есть, ожидается его
восстановление в локальном сторе.

Очередь занятой сессии обрабатывается следующими ходами. Приемник не прерывает
текущий ход. После ошибки хода оставшиеся сообщения собственной очереди запускает
`thread/queue/start`. Настройки модели, прав и рабочего каталога не переопределяются.

## Запуск и остановка

Нужны Linux, работающий Codex daemon, настроенный stdio-профиль `paranoia-cli`
и собранный EasyCli. Python 3.11+ нужен только обертке чтения существующего конфига;
сама доставка выполняется Rust-бинарем. Обертка передает секреты через окружение.

```bash
cargo build --release --locked --manifest-path ParanoiaEasyCli/Cargo.toml -j 8

python3 ParanoiaEasyCli/codex-channel.py \
  --binary /absolute/path/to/paranoia-easy-cli \
  --thread EXISTING_THREAD_ID \
  --topic 'Имя темы' \
  --after-message ALREADY_HANDLED_MESSAGE_ID
```

Рабочий MCP и конфигурация Codex остаются прежними. Для постоянного запуска ту же
команду помещают в отдельный пользовательский systemd unit; `Restart=on-failure`
перезапускает приемник с сохраненным состоянием. Остановка этого unit отключает
автодоставку. Сессия Codex и ручные MCP-инструменты остаются доступны. После
возобновления запускают ту же команду; курсоры не удаляют и бинарь живого MCP не заменяют.

Для новой сессии unit можно подготовить отдельно от его запуска:

```bash
python3 ParanoiaEasyCli/codex-channel-unit.py \
  --binary /absolute/path/to/paranoia-easy-cli \
  --thread EXISTING_THREAD_ID \
  --topic 'Имя темы' \
  --after-message ALREADY_HANDLED_MESSAGE_ID \
  --output-dir /absolute/path/to/prepared-units
```

Из инструмента текущего агента `--thread` можно опустить: используется
`CODEX_THREAD_ID`. В обычном терминале ID задают явно. Генератор не читает секреты,
не запускает сервис и не перезаписывает существующий unit. Команды включения и
отключения печатаются в ответе. Сессии выделяют собственную тему; начальной
отметкой служит уже обработанное сообщение, а не произвольное новое.
Рабочий каталог задает `cwd` MCP-профиля; без него user-unit работает из домашнего
каталога пользователя. Пути в MCP-профиле должны учитывать это правило.

Состояние рядом с БД:

```json
{
  "seq": 10,
  "pending": {
    "seq": 12,
    "message_id": "message-id",
    "reaction_sent": true,
    "submitted": true
  }
}
```

`seq` — последний подтвержденный номер; `pending` — ожидающее сообщение.
Файл `.paranoia-codex-<binding hash>.json` не содержит текста или секретов.
Журнал неопределенности показывает message_id, client_id, seq и путь этого файла.

## Ручное разрешение неопределенности

1. Остановить только приемник. Сохранить копию указанного в журнале файла состояния.
2. В том же thread проверить все страницы `thread/queue/list` и `thread/items/list`
   по точному client_id из журнала: поля `clientUserMessageId` и `item.clientId`.
   Если ID найден, достаточно обычного перезапуска приемника: он подтвердит доставку.
3. Если ID не найден, дождаться завершения ожидающих ходов и повторить проверку.
   Пустой результат сразу после обрыва не доказывает недоставку. Проверить также
   переписку: сообщение могло быть обработано, а затем удалено пользователем.
4. Если пользователь подтвердил необходимость повторной доставки именно этого
   message_id, в остановленном приемнике изменить только его `pending.submitted`
   на `false`, оставив `seq`, `pending.seq` и `reaction_sent` неизменными, и запустить
   приемник. Поздняя доставка первоначального запроса все еще может дать дубль.
   При неустановленном исходе оставить состояние ожидающим; не сбрасывать курсор.

## Проверки

```bash
cargo test --offline --locked --manifest-path ParanoiaEasyCli/Cargo.toml -j 8 codex_channel
python3 ParanoiaEasyCli/tests/codex_protocol.py
python3 -m unittest discover -s ParanoiaEasyCli/tests -p test_codex_channel_unit.py
```

Второй прогон создает временный профиль Codex и локальный Responses API. Прокси
теряет ответ принятого `queue/add`, затем тот же приемник восстанавливается из
сохраненного состояния. Рабочие аккаунты, сокет daemon и БД Paranoia не используются.
Живой сквозной тест выполняется отдельно: сообщение выбранной темы должно попасть
в существующий thread и получить реакцию без дополнительного ввода в терминал.

## Метрики

Отдельных метрик нет. Диагностика в stderr содержит состояние подключения и
неопределенные отправки; текст сообщений и конфигурация в нее не выводятся.
