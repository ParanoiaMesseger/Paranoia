# Политика реализации системы уведомлений

## Обзор

Данный документ описывает архитектурные решения, протокол и платформенную реализацию системы уведомлений мессенджера Paranoia. Все решения приняты в рамках действующей модели угроз: сервер считается потенциально скомпрометированным, Google/Apple не являются доверенными сторонами, self-hosted развёртывание является основным режимом работы.

---

## 1. Принципы системы уведомлений

### 1.1. Что сервер не должен знать

- Количество устройств пользователя
- Платформу и тип устройства (iOS, Android, Desktop)
- Push-токены (FCM, APNs) — они не используются
- От кого пришло сообщение и его содержимое
- Факт прочтения сообщения

### 1.2. Что сервер неизбежно знает

- IP-адрес клиента в момент polling-запроса
- Время запроса
- Идентификатор диалога и последний известный клиенту `seq` (передаётся в `/notify`)

Эти метаданные признаются допустимым компромиссом, задокументированным в разделе 5.3 модели угроз (корреляция по IP/времени).

### 1.3. Отказ от FCM и APNs

FCM и APNs не используются по следующим причинам:
- Self-hosted развёртывание не имеет Developer-сертификата Apple
- Google и Apple становятся наблюдателями в цепочке доставки
- FCM/APNs требуют хранения device-токенов, связанных с аккаунтом

## 2. Серверный протокол — эндпоинт `/notify`

### 2.1. Место в API

К существующим эндпоинтам `/reg`, `/push`, `/pull`, `/determinate` добавляется новый:

```
PUT /notify
```

### 2.2. Формат запроса

Эндпоинт работает в двух режимах; ветка выбирается по наличию непустого `items` (shape-detect на сервере).

**Одиночный режим** (один диалог). Запрос аналогичен `/pull` по структуре подписи: клиент передаёт идентификатор партнёра и последний известный ему `seq`:

```json
{
  "sender":       "alice",
  "partner":      "bob",
  "seq":          42,
  "sig":          "<Ed25519_SIGN(sender||partner||seq)>",
  "long_poll_ms": 0
}
```

Подпись покрывает `sender`, `partner`, `seq`. Сервер проверяет подпись по публичному ключу `sender`. `make_dialogue_id(sender, partner)` всегда включает `sender`, поэтому запросить можно только СВОИ диалоги.

**Multi-режим** (N диалогов одним запросом — экономия батареи, см. § 2.5). Поле `partner`/`seq` пустые, список диалогов передаётся в `items`:

```json
{
  "sender":       "alice",
  "sig":          "<Ed25519_SIGN(sender || (partner||seq)*)>",
  "long_poll_ms": 15000,
  "items": [
    { "partner": "bob",   "seq": 42 },
    { "partner": "carol", "seq": 7  }
  ]
}
```

Подпись одна — `sender` над канонической конкатенацией `(partner‖seq)` по порядку элементов. Потолок — 512 диалогов на запрос (`MAX_NOTIFY_ITEMS`); незарегистрированные партнёры тихо пропускаются, не валя весь батч.

`long_poll_ms` НЕ входит в подпись (величина капается сервером параметром `notify_long_poll_max_ms` и прав не несёт). При `0`/отсутствии — мгновенный ответ; при `>0` сервер удерживает соединение (long-poll) до появления нового сообщения в любом из диалогов либо до истечения времени.

### 2.3. Формат ответа

**Одиночный режим:**

```json
{ "success": true, "n": 3, "message": "", "items": [] }
```

Где `n` — количество сообщений, считающихся для `sender` новыми (с `seq` строго больше `max(переданный_seq, last_seq[sender])`; см. § 2.4 о дедупликации собственных/прочитанных-на-другом-устройстве). Если `n = 0` — новых нет.

**Multi-режим:** `n = 0`, а зажжённые диалоги (с `n > 0`) перечислены в `items`:

```json
{ "success": true, "n": 0, "message": "", "items": [ { "partner": "bob", "n": 3 } ] }
```

Сервер не передаёт содержимое, идентификаторы отправителей, текст или иные метаданные — только хеши `dialogue_id` (неявно, через сопоставление) и счётчики.

### 2.4. Дедупликация: «новое» относительно собственного `last_seq`

Сервер считает новыми только сообщения с `seq` выше `last_seq[sender]` — высшей позиции, которую этот аккаунт уже видел. `last_seq` поднимается и при `pull` (на любом устройстве аккаунта), и при `push` собственного сообщения (pull-before-push гарантирует, что отправитель прочитал всё до своего `seq`). Поэтому:

- собственное отправленное сообщение НЕ всплывает уведомлением на других устройствах того же аккаунта;
- сообщение, прочитанное на устройстве B, не присылает повторное уведомление на устройство A.

Это поведение опирается на server-side read-seq (`receipt_state`) — то же значение, что отдаётся как `own_last_seq` в `GET /arrived` (см. MessageDeliveryStatusPolicy).

### 2.5. Multi-notify и батарея

Фоновый сервис следит сразу за всеми диалогами профиля. Вместо «N диалогов = N HTTP-запросов» клиент группирует диалоги по сессии и шлёт ОДИН multi-`/notify`. Long-poll просыпается на ПЕРВОМ зажёгшемся диалоге. Это снижает число пробуждений радиомодуля и расход аккумулятора.

### 2.6. Cover-слой

Запрос и ответ проходят через маскарадный cover-слой (раздел 4.3 модели угроз) наравне с остальными эндпоинтами. Внешний вид JSON-полей определяется активным cover-модулем.

## 3. Клиентский механизм — randomized polling

### 3.1. Алгоритм

Используются два режима polling, в зависимости от состояния приложения.

**Передний план (приложение открыто)** — короткий рандомизированный цикл без удержания соединения (`long_poll_ms = 0`):

```
interval = random(2, 15) секунд   // NotificationCoordinator::randomNotifyDelayMs
```

**Фон (приложение свёрнуто/закрыто)** — long-poll: сервер удерживает запрос до нового сообщения либо `MSG_LONG_POLL_MS = 15 c`, а планировщик перезапускает цикл точным alarm'ом каждые `POLL_INTERVAL_MS = 60 c` (см. § 4.2). Соседние long-poll'ы дают практически непрерывное покрытие входящих в пределах ограничений ОС (Doze).

Рандомизация интервала и серверный jitter (§ 6.1) преследуют две цели:
- Снижают корреляцию между отправкой сообщения и моментом запроса `/notify` — затрудняют traffic correlation attack
- Снижают предсказуемость паттерна запросов при DPI-анализе

### 3.2. Поведение при получении `n > 0`

При `n > 0` клиент **не загружает сообщения немедленно**. Показывается только системное уведомление:

```
"Новых сообщений: N"
```

Без имени отправителя, без текста, без идентификатора диалога. Содержимое подгружается через `/pull` только когда пользователь открывает конкретный диалог.

### 3.3. Поведение при `n = 0`

Планируется следующий polling-запрос через новый случайный интервал. Никаких дополнительных действий.

### 3.4. Reconnect-стратегия

При потере соединения или ошибке сети — exponential backoff с jitter:

```
delay = min(1000 * 2^retry_count, 60000) мс
delay += random(0, delay * 0.2) мс  // jitter ±20%
```

При обнаружении смены сети через системное API (`QNetworkInformation`) — счётчик retry сбрасывается, переподключение немедленное.

## 4. Платформенная реализация

### 4.1. Linux и Windows — системный трей

Приложение работает в системном трее после закрытия основного окна. Polling выполняется в фоновом потоке штатными средствами Qt без ограничений ОС.

- **Уведомления:** `QSystemTrayIcon::showMessage()` — нативные уведомления (Action Center на Windows, libnotify/D-Bus на Linux)
- **Фоновый процесс:** обычный `QTimer` в отдельном потоке
- **Поведение при закрытии окна:** `closeEvent` переопределяется — приложение скрывается в трей, процесс не завершается

### 4.2. Android — Foreground Service в отдельном процессе

Polling выполняется в Android Foreground Service `ParanoiaForegroundService`, который устойчив к battery optimization и Doze mode.

- **Индикатор:** системное уведомление в статус-баре (обязательное требование Android 8+), канал `paranoia_polling`
- **Отдельный процесс:** сервис объявлен `android:process=":notifications"` — НЕ тянет за собой инициализацию Qt/main-процесса. Это Qt-free Java-сервис, вызывающий Rust-ядро напрямую через JNI (`paranoiaServiceNotifyMultiWait` и др.), без `QAndroidService`.
- **Snapshot-модель:** сервис держит в RAM только минимум для подписи `/notify` (signing-ключ, server_id, last_pulled_seq по диалогам). Сессионных ключей диалога, master_key, db_key у сервиса НЕТ; после reboot/kill снимок исчезает, UI пушит свежий при следующем unlock'е.
- **Цикл:** `AlarmManager` с точным alarm'ом (`POLL_INTERVAL_MS = 60 c`) + `WAKE_LOCK` на время запроса; внутри — multi-notify long-poll (`MSG_LONG_POLL_MS = 15 c`, hard-timeout `75 c`).
- **`foregroundServiceType`:** `remoteMessaging|dataSync`
- **Разрешения в манифесте:** `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_DATA_SYNC`, `FOREGROUND_SERVICE_REMOTE_MESSAGING`, `POST_NOTIFICATIONS`, `USE_EXACT_ALARM`, `SCHEDULE_EXACT_ALARM`, `WAKE_LOCK`

### 4.3. iOS 13+ — BGProcessingTask

Фоновый опрос реализован через `BGTaskScheduler` + `BGProcessingTaskRequest` (iOS 13+) — API, парное к режиму `UIBackgroundModes = processing` в `Info.plist` (правка plist сверх этого не нужна). Это best-effort: частоту запуска выбирает система, реал-тайма без push не будет (и не должно быть — push исключён моделью угроз).

- **Идентификатор задачи:** `com.paranoia.polling` (в `BGTaskSchedulerPermittedIdentifiers`)
- **Параметры запроса:** `requiresNetworkConnectivity = YES`, `requiresExternalPower = NO`, `earliestBeginDate = +60 c`
- **Поведение:** задача регистрируется при старте и самостоятельно перепланируется в начале каждого запуска (`handlePollingTask` → `schedulePollingTask`); один прогон триггерит фоновый poll и завершается хард-стопом через 30 c
- **Реализация:** Objective-C++ (`.mm`), вызывается из Qt через `extern` функцию

**Почему именно BGProcessingTask, а не альтернативы:**
- `BGAppRefreshTask` — потребовал бы режим `fetch`, которого в plist нет → `submitTaskRequest` падал бы `BGTaskSchedulerErrorCodeNotPermitted` (был реальный регресс «фон пропал»)
- `BGContinuedProcessingTask` (iOS 26) — предназначен для user-initiated work, для периодического опроса не годится
- `NEPacketTunnelProvider` (VPN-хак) — конфликтует с реальными VPN-сервисами пользователя, неприемлемо для целевой аудитории
- APNs — требует серверного хранения device-токена, нарушает модель угроз

### 4.4. iOS < 13 — без фоновых уведомлений

На iOS ниже 13 (`BGTaskScheduler`/`BGProcessingTaskRequest` недоступны) фоновые уведомления **не реализуются** — уведомления работают только пока приложение открыто. При первом запуске на таких версиях один раз показывается информирующий алерт.

> ⚠️ В коде текст этого алерта (`PlatformNotifications_ios.mm`) до сих пор ссылается на «iOS 25/iOS 26», хотя фактический порог — iOS 13 (`supportsBackgroundTasks()`). Строку алерта стоит поправить — расхождение не в этой политике, а в самом ресурсе.

## 6. Угрозы, которые система не устраняет

### 6.1. Traffic correlation attack

Наблюдатель, контролирующий трафик обоих участников, может сопоставить момент отправки сообщения одним с моментом получения `n > 0` другим. Рандомизированный интервал polling (2–15 с на переднем плане) и long-poll в фоне **снижают**, но не исключают эту корреляцию.

**Частичное решение на сервере:** случайная задержка ответа `/notify` на 0–N секунд (jitter на стороне сервера) дополнительно разрывает корреляцию.

### 6.2. IP-раскрытие

Polling-запросы к серверу раскрывают IP клиента и факт активности. Для защиты требуются внешние средства: VPN, Tor, Project-X (XRAY) — вне scope данного документа, задокументировано в разделе 5.7 модели угроз.

### 6.3. Анализ частоты запросов

Специализированные DPI-системы с ML могут выучить паттерн случайных polling-запросов. Cover-слой (раздел 4.3) снижает стоимость детекции, но не устраняет угрозу полностью.

## 7. Допущения и компромиссы

- **Задержка уведомления:** на переднем плане 2–15 с; в фоне — в пределах окон, которые выделяет ОС (Android: ~60 с цикл + 15 с long-poll; iOS: best-effort по решению системы)
- **Дополнительный round-trip:** `/notify` добавляет нагрузку на сервер; multi-notify (§ 2.5) схлопывает N диалогов в один запрос, снижая её; при необходимости — rate limiting на эндпоинт
- **iOS < 13:** отсутствие фоновых уведомлений — явный и задокументированный компромисс, сообщаемый пользователю при первом запуске
