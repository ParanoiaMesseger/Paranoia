# План исправлений: последовательность и группировка

Сквозной план поверх находок из [01-freezes](01-freezes.md) / [02-redundant](02-redundant.md) / [03-artifacts](03-artifacts.md).
Ссылки вида `01#32` = файл 01-freezes, пункт 32.

**Главный принцип:** не чинить 149 пунктов поштучно. Большинство схлопывается в ~10 «keystone»-фиксов, где одно изменение закрывает группу. Сначала строим общую инфраструктуру (async-воркер, единый рантайм, RAM-кэш манифеста, узкий ffiMutex), потом она гасит десятки пунктов почти механически.

Обозначения размера: **S** (часы) · **M** (~день) · **L** (несколько дней) · **XL** (неделя+).
Риск: 🟢 механический/grep-проверенный · 🟡 смена поведения, нужна проверка · 🔴 конкурентность/wire-формат/крипта — careful design + верификация.

## 1. Карта общей инфраструктуры (один фикс → группа пунктов)

| Keystone-фикс | Закрывает / гасит | Где строим |
|---|---|---|
| **A. Async `saveDialogs`** (снимок `QList<Dialog>` по значению → сериализация+vault_encrypt+запись на QThreadPool, last-write-wins, коалесинг) | `01#7`, `01#12` целиком; убирает saveDialogs-стоимость внутри `01#9`, `01#11`, `01#27` | `ServerSession::saveDialogs` — один метод, ~15 колл-сайтов |
| **B. Хелпер «тяжёлый Q_INVOKABLE → воркер + сигнал результата»** | шаблон для `01#8`, `01#9`, `01#10`, `01#11`, `01#27`, `01#29`, GUI-половина `01#6` | образцы уже есть — `doVaultChangePinAsync`, `clearCaches` |
| **C. Единый процессный `OnceLock<Runtime>` + кэш `Transport` по (server, reserves)** | `02#15`, `02#33`, `02#34` (три батарейные находки, одна high) | новый static; прецедент `voip_ffi.rs:86` `VOIP_RUNTIME` |
| **D. Событийная отмена `race_shutdown`** (`tokio::sync::Notify` вместо 100мс-поллинга) | `02#16` (все long-poll-обёртки) | `ffi.rs:59-69` + `paranoia_begin_shutdown` |
| **E. ⭐ Сужение `ffiMutex`** (лок только на указатель `session->ffi`; сетевые операции без общего лока; тема — явным параметром FFI) | конвой из `01#32`; гасит contention-половину `01#5`, `01#6`, `02#6`, `02#8` | `ChatBackend`/`MainBackend`/FFI send-варианты |
| **F. RAM-кэш манифеста профилей** (загрузка раз на операцию + кэш с инвалидацией по `sessionsChanged`) | `02#5`, `02#25`, `02#14`, манифест-часть `01#27` | `Utils`/`MainBackend` |
| **G. `verify_pair_signature` хелпер** | `03#3` (dbg!) + тройной дубль sig-блока | `routes/mod.rs`/`crypto.rs` |
| **H. Общие QML/JNI-компоненты** (`ConfirmPopup`, `PinKeypad`, JNI-SAF, STUN-примитивы, `QrScanFlow`) | `03#62`, `03#39`, `03#64`, `03#65`, `03#45`, дубль QR-декода | ui/Components, utils |

**Что ⭐E субсумирует, но НЕ закрывает полностью:** сужение ffiMutex убирает *contention* (минутные стопы при аплоаде), но синхронная работа на GUI-потоке в `01#5`/`01#6` остаётся — её добивает пакет **B/A** (вынос на воркер). Т.е. E и A/B **дополняют** друг друга, порядок между ними — E проектируем первым (влияет на сигнатуры FFI send).

## 2. Этапы (критический путь)

Этапы 4–8 — независимые треки (Rust-ядро, платформа, VoIP, ИБ, сервер), могут идти параллельно клиентским 1–3 разными сессиями/днями. Клиентские 1→2→3 идут по порядку (общие файлы MainBackend/ChatBackend).

### Этап 0 — Быстрые корректностные фиксы 🟢 S (каждый — свой микрокоммит)

Почти нулевой риск, часть — реальные баги. Ландить первыми: моментум + де-риск.

- **`03#1` reg.rs `config_path()`** — ⚠️ **фактический баг**: с `PARANOIA_CONFIG` регистрации теряются после рестарта. Одна строка. **Приоритет №1.**
- **`01#2` save конфига под локом** — сериализовать в строку, `drop(guard)`, `tokio::fs::write`. Снимает server-wide стойл.
- **`03#8` checkTurnServer** — ложноположительный «доступен» для любого адреса → нейтральный статус «сохранён, не проверялось».
- **`03#30` висящий бейдж** (combinedCount==0) — реальный UX-баг: прочитанный с другого устройства диалог держит бейдж.
- **`03#72` vaultSetPinResult** — молчащая ошибка установки PIN → подключить обработчик в SetPin.
- **`01#18` InstallServerBackend usleep(1мс)** — флап установщика → `QTimer::singleShot`.
- Тривиальные: `03#3` dbg!→warn! (или через G), `03#4` unsafe impl, `03#49` `Push failed: {msg}`, `03#27` ArrivedResponse.ts, `03#28` HKDF-константа.

### Этап 1 — ⭐ Корневой рефактор ffiMutex (keystone E) 🔴 L

Самый ценный и самый рисковый. Проектировать первым — влияет на сигнатуры FFI.

- **Закрывает:** `01#32`; contention-половина `01#5`, `01#6`, `02#6`, `02#8`.
- **Подход:** (1) FFI send-варианты с явным параметром темы (слот `active_topic` уже есть) — убрать компоновку `set_active_topic → send` из-под лока; (2) длинные сетевые (send_file*, send_photo_grouped*, receive, resume, save_attachment, history) — БЕЗ per-session ffiMutex; (3) при необходимости узкий лок только на исходящие push одного диалога (порядок seq); (4) `ffiMutex` оставить лишь на защиту указателя `session->ffi`; (5) поправить комментарии «handle !Send».
- **Опора:** хэндл фактически Send+Sync, уже 4 конкурентных вызова в проде (ActiveChatNotifier long-poll, pollActiveChat, NotificationCoordinator, CallSignalingClient).
- **Риск 🔴:** порядок seq исходящих. Обязательна проверка: отправка файла во время приёма батча; параллельные отправки в один диалог; отсутствие duplicate_seq/порчи.
- **Рекомендация:** выкатывать за временным флагом; сохранить старый путь до подтверждения на боевых устройствах.

Крупнейший кластер по числу пунктов; закрывает большинство клиентских фризов.

- **A (сначала):** async `saveDialogs` → `01#7` + `01#12` одним фиксом.
- **B (шаблон-хелпер, потом каждый на нём):** `01#8` importProfile, `01#29` exportProfile, `01#9` deleteProfile (+ teardown SQLCipher на воркер), `01#27` changeProfileServer, `01#10` storageBreakdown, `01#11` bakeCircleAvatarBase64 (+ `QImageReader::setScaledSize`), `01#6` GUI-половина маскировки.
- **Отдельно, тот же этап:** `01#13` parseMessages на воркере (образец `prefetchAllDialogs`); `01#5` publishServiceSnapshot — RAM-кэш last_pulled_seq вместо FFI в цикле; `01#20` Hunspell — шаренный синглтон + ленивая загрузка на фоне.

### Этап 11 — Полевые UX-замечания пользователя (21.07) 🟢🟡 S–M (клиент)

Не из review-пайплайна — прямые полевые репорты. Мелкие, user-visible, в основном независимы от больших рефакторов (кроме `U1`, задевающего notify/dialogs-путь). Хорошие «быстрые победы» — можно делать вперемешку с Этапом 0. `U2`/`U3+U4`/`U5` — чистый QML (`ChatPage.qml`, `TextMessageViewer.qml`), не трогают threading.

- **`U1` (а) — превью диалога не обновляется в фоне** 🟡 M.
  - *Симптом:* при входе в мессенджер плашка диалога показывает СТАРОЕ последнее сообщение, хотя бейдж уведомления горит. Вводит в заблуждение.
  - *Причина:* превью = кэш `Dialog::lastMsg` (`src/session/Dialog.hpp:22`), отдаётся `MainBackend::getDialogs()` (`src/backend/MainBackend.cpp:1227`), рисуется `ui/Pages/MainPage.qml:796`. Пересчитывается ТОЛЬКО в `ChatBackend::appendMessages` (`src/backend/ChatBackend.cpp:2779`) — после расшифровки тел, т.е. при `openChat→fetchMessages` или bulk `prefetchAllDialogs`. `prefetchAllDialogs` подключён лишь к `MainBackend::vaultUnlocked` (`src/main.cpp:206-207`) → срабатывает на холодный старт/PIN, но НЕ на возврат из фона и НЕ на приход уведомления. Notify-поллинг (`NotificationCoordinator::applyNotifyCounts`, `src/backend/NotificationCoordinator.cpp:407`) получает от `notify_unread_multi_keyring` только СЧЁТЧИК (`:364`) → обновляет бейдж/сортировку/точку и шлёт `dialogsChanged()`, но `lastMsg` не трогает. Отсюда контраст «бейдж горит — превью замёрзло».
  - *Подход (батарейно-осознанный):* при переходе в active (`ChatBackend::onApplicationStateChanged`, `ChatBackend.cpp:2295`) при разблокированном хранилище — таргетно обновить `lastMsg` только для пиров с непрочитанным (набор известен notify-слою: `m_notifiedPendingByPeer`), реюзая `appendMessages`-путь; коалесинг/порог, чтобы не дёргать на каждый resume. НЕ слепой `prefetchAllDialogs` по всем пирам.
  - *Альтернативы:* (проще, тяжелее) звать `prefetchAllDialogs` на foreground — цикл `receive_keyring` по ВСЕМ пирам, бьёт батарею, пересекается с `02#5`/`01#1`, не рекомендую. (Глубоко, будущее) расширить notify-API коротким превью — тогда без доп. receive, но это протокол+Rust-ядро, вне scope.
  - *Риск 🟡:* доп. сетевые на foreground — ограничить изменившимся набором. *Проверка:* фон→уведомление→вход, превью совпадает с бейджем; resume НЕ порождает N receive по всем диалогам. Пересекается с Этапом 3 (модель списка) и Этапом 5 (фоновые режимы).

- **`U2` (б) — колёсико не листает бар тем на десктопе** 🟢 S.
  - *Причина:* `topicBar` — горизонтальный `Flickable` (`ChatPage.qml:3019-3027`, `flickableDirection: Flickable.HorizontalFlick`); в `ChatPage.qml` НЕТ ни одного `WheelHandler`/`onWheel`. `HorizontalFlick` слушает только `angleDelta.x`, обычное колесо шлёт `angleDelta.y` → бар стоит.
  - *Подход:* `WheelHandler` на `topicBar`, мапящий `angleDelta.y`(+`.x`) в `contentX` с clamp по `contentWidth` (образец — `PhotoViewer.qml:199`, `TextMessageViewer.qml:255`). ~10 строк. *Риск 🟢, только десктоп.*

- **`U3`+`U4` (в+г) — просмотрщик: зум колесом и герметизация ввода** 🟡 S–M — ОДИН фикс.
  - *Симптомы:* (в) нет Ctrl+колёсико зума; (г) листание в просмотрщике проваливается в свайп тем под окном → при выходе тема уже другая.
  - *Диагноз:* Ctrl+колёсико зум ЕСТЬ с 0.2.15 (`TextMessageViewer.qml:255-262`), но `WheelHandler` — ребёнок `bodyFlick`, покрывает только тело (не шапку 52px/футер 48px/поля колонки); оверлей НЕ модальный — фон-`MouseArea` (`:91-95`) без `onWheel`/`preventStealing`. → wheel над шапкой/футером и горизонтальный wheel/drag протекают на `topicBar` (`ChatPage.qml:3019`) и на свайп тем `DragHandler topicSwipe` на `messageListPane` (`ChatPage.qml:3136`, порог 26px, `enabled` не учитывает открытый просмотрщик). Отсюда «зум не срабатывает» (курсор вне тела) И «тема сменилась» (drag протёк вниз) — одна причина.
  - *Подход (герметизация):* (1) поднять зум-`WheelHandler` на root оверлея (Ctrl+wheel зумит над всей площадью); (2) на root — «глотающий» `WheelHandler` без модификатора с `event.accepted=true` (не-Ctrl колесо не течёт вниз); (3) загейтить свайп: `topicSwipe.enabled: … && !textViewer.visible` (`ChatPage.qml:3139`), и `topicBar` тоже; либо `preventStealing` на оверлее. (4) проверить, что Flickable не крадёт Ctrl+wheel.
  - *Риск 🟡:* доставка wheel в Qt Quick капризна — обязателен ручной тест на десктопе. *Проверка:* Ctrl+колесо зумит везде в просмотрщике; обычное колесо/горизонтальный жест НЕ меняют тему; при выходе тема прежняя.

- **`U5` (д) — сортировать темы по дате последнего сообщения** 🟡 S–M.
  - *Причина:* `_topicNames` строится в порядке ПЕРВОГО появления (`ChatPage.qml` `_rescanTopics` 994-1017, «порядок появления» 1006); модель чипов (3058-3068) берёт как есть; «Все»/«Главная» закреплены первыми.
  - *Подход:* считать per-topic `max(ts)` по кэшу (кэш ts-возрастающий, свежие всегда в окне `ORDER BY ts DESC LIMIT n`), сортировать `_topicNames` по убыванию last-ts; «Все»/«Главная» — закреплены; синхронизировать `topicOrder()` (1101-1108) для свайпа; `_pendingNewTopic` — первой.
  - *Ограничение:* если последнее сообщение темы за окном загрузки — last-ts приблизителен; но свежая активность всегда в окне (DESC LIMIT), для «куда пришло» точно.
  - *Риск 🟡:* перестановка чипов на каждое новое сообщение — точечно, не мигать; активная тема не должна «прыгать» под пальцем. Пересекается с `U1` и Этапом 3. *Опция сверх запроса:* per-topic точка-непрочитанного на чипе — сразу видно КУДА пришло (отметить как расширение).
